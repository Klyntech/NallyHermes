# NallyHermes V2.2 Roadmap

## Release intent

V2.2 turns Nally from a capable Telegram agent into a more useful personal operating companion for Clinton: better at choosing and coordinating work, better at coding, better at general assistance, better at law-school life, and able to operate across Notion, Gmail, and Nallputer without weakening the hand-built orchestra’s safety boundaries.

The release continues the no-framework strategy. Every new capability must fit the existing custom orchestra, typed executor, per-user scope, explicit approval policy, and evidence-based completion reporting.

## Current status: alpha.1 foundation complete

The first foundation slice is implemented. Memories now support typed categories, entity fields, confidence, source, expiry, and confirmation metadata. Relevant durable context is loaded before model routing for requests that contain incomplete references. The `notion`, `gmail`, and `nallputer` dynamic dispatcher contracts are registered with executor validation, workflow allowlist support, credential fail-closed behavior, and explicit write gates.

The provider adapters themselves remain intentionally unimplemented in this slice: configured calls return a clear contract-only response rather than pretending that an external action succeeded. The next slice implements Notion and Gmail read operations, followed by bounded Nallputer operations.

## 1. Improved orchestra

### Core changes

- Add an explicit **context phase** before routing: active topic, relevant memories, current entities, user preferences, and unresolved commitments.
- Add **capability planning**: decide whether a request needs conversation, one tool, parallel reads, a dependent plan, a workflow, or an interactive coding session.
- Add **entity continuity**: resolve “our next match” to the club stored as the user’s favorite club, while asking when more than one entity is plausible.
- Add **tool portfolio selection**: choose the minimum connector set needed for the task and avoid unnecessary provider calls.
- Add **evidence checkpoints** after every mutation and before claiming completion.
- Add **budget-aware degradation**: return useful partial results when a provider or model budget is exhausted.
- Add **resume state** for interrupted multi-step work.
- Add connector health and latency telemetry without exposing internal narration to the user.

### Acceptance criteria

- Ordinary conversation remains fast and does not invoke the planner unnecessarily.
- Multi-step tasks show one coherent result instead of a transcript of internal steps.
- Provider failures produce an honest partial result and a next action.
- Mutations are never retried blindly.
- The orchestra can later support voice without redesigning tool contracts.

## 2. Improved coding abilities

Nally should become a safe coding partner for the user’s workspace and Nallputer:

- Inspect repository structure and understand project conventions.
- Read, search, and compare code across files.
- Plan a change before editing.
- Make bounded patches with diff previews.
- Run typechecks, tests, builds, and targeted diagnostics.
- Explain failures in plain language.
- Keep an execution record of commands, files changed, and validation evidence.
- Support rollback or patch reversal where possible.
- Never expose secrets or execute destructive commands without explicit approval.

Coding work should use a coding-specific orchestra mode with file scope, command scope, timeout, output limits, and approval policy.

## 3. Improved assistant abilities

- Better current-information research and source synthesis.
- Better email drafting, triage, and follow-up suggestions.
- Notion page and database assistance.
- Calendar-aware planning across tasks, classes, and deadlines.
- Durable daily briefings with bounded source lists.
- Proactive but opt-in follow-ups.
- Clear distinction between facts, preferences, plans, and uncertain inferences.
- Better natural responses that preserve Nally’s identity without capability tours or robotic disclaimers.

## 4. Improved Student Companion

The law-student companion should use the user’s actual academic context:

- Grounded Q&A over ingested PDFs with source/document references.
- Case briefs: facts, issue, rule, application, holding, and significance.
- Statute and section extraction with quoted source context.
- IRAC and problem-question assistance.
- Course-aware explanations and revision plans.
- Timetable-aware daily briefings.
- Assessment deadline planning.
- Spaced review prompts and weak-topic tracking.
- Study-session workflows with bounded sources and output destinations.
- Clear labels for extracted source facts versus Nally’s explanation or inference.

## 5. Notion connector

Expose one dynamic `notion` dispatcher following the GitHub pattern:

```text
list_operations → get_operation → call_operation
```

Initial scope:

- Search pages and databases
- Read a page
- Read a block tree
- Query a database
- Create a page
- Append blocks
- Update page properties
- Archive a page only with explicit approval

Authentication must use a server-side Notion integration token. Workspace and database scope must be configurable. Retrieved Notion content is untrusted data, not instructions.

## 6. Gmail connector

Expose one dynamic `gmail` dispatcher with strict privacy and mutation boundaries.

Initial scope:

- Search messages and threads
- Read message metadata and bodies
- List labels
- Draft an email
- Update draft
- Send only with explicit approval
- Archive or label messages only with explicit approval

Gmail must default to least-privilege OAuth scopes, redact secrets from logs, cap body and attachment sizes, and distinguish drafts from sent messages. No destructive delete operation should be exposed in the first V2.2 release.

## 7. Nallputer connector

Nallputer is the user’s customized VM and must not be treated as an unrestricted shell.

Expose one dynamic `nallputer` dispatcher with:

- Host health and capability discovery
- Workspace file inspection
- Bounded command execution
- Process and service status
- Test/build execution
- Logs with size limits
- Artifact retrieval
- Explicit approval for writes, package installation, network access, service restarts, and destructive commands

Every command must include a working directory, timeout, output limit, environment policy, and approval policy. Secrets must never be returned in command output or persisted in logs.

## 8. Improved memory system

### Memory model

Separate durable context into typed records:

- `fact`: stable personal information, such as favorite club
- `preference`: communication, study, or output preference
- `project`: ongoing work and decisions
- `commitment`: promises, deadlines, and follow-ups
- `entity`: clubs, courses, people, repositories, documents, and organizations
- `episode`: useful recent interaction context

Each record needs confidence, source, last-confirmed time, freshness, and optional expiration.

### Active memory application

The orchestra should retrieve relevant memory before tool selection when the current request contains an incomplete reference. Example:

```text
User: My favorite club is Real Madrid.
Nally: Got it — I’ll remember that your favorite club is Real Madrid.

User: When is our next match?
Nally: Real Madrid’s next match is ...
```

The second request should resolve `our club` through memory and then use a current sports source. Nally must not invent a fixture if the remembered entity is ambiguous or current information is unavailable.

### Memory safeguards

- Ask before storing sensitive information.
- Confirm or lower confidence when facts conflict.
- Prefer newer explicit user corrections.
- Do not surface unrelated memories.
- Do not treat memory as proof of current external facts.
- Explain briefly when a memory influenced an answer only when useful.
- Keep structured records and LightRAG semantic retrieval synchronized.

## Non-negotiable boundaries

- No orchestration framework.
- No unrestricted shell.
- No provider token accepted from chat.
- No connector content treated as instructions.
- No silent destructive mutations.
- No unsupported current facts inferred from memory.
- No claim of completion without provider evidence.
