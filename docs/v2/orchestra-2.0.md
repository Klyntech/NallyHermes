# Orchestra 2.0

Status: implementation design
Branch: `v2`
Scope: strengthen the existing custom orchestration engine without replacing it or changing the model-visible tool set.

## Current implementation

The current engine is a model-led controller with:
- a planning pass that optionally decomposes multi-step requests into a validated DAG;
- a direct execution loop when decomposition is unnecessary or planning fails;
- bounded parallel execution for read-only plan steps and read-only tool calls;
- serialized mutation execution;
- per-tool schema validation and bounded transient retries for read-only calls;
- a final synthesis pass that reports partial work rather than claiming completion;
- progress events consumed by the Telegram presentation layer.

The engine currently lives primarily in `controller.ts`, with planning, tool execution, evaluation, context assembly, and progress formatting split across adjacent modules. This is a sound v1 foundation, but controller responsibilities and execution state are still tightly coupled.

## Findings to address

### P0 — correctness and safety

1. **Step-local evidence is not isolated.** `runPlannedStep` determines whether it has evidence by searching all messages for any tool result. Because each step receives a copy of the shared conversation, old tool messages can incorrectly make a step appear partial even when that step produced no observation. Track evidence generated by the current step only.
2. **Recovered prerequisites do not reopen dependents.** The scheduler marks dependent steps blocked after a prerequisite fails. A later recovery pass can change the prerequisite outcome to completed, but does not re-evaluate the dependency graph. Recovery must update readiness and allow newly unblocked steps to run within the remaining budget.
3. **Budget units are ambiguous.** The plan budget currently increments once per model tool-call round, although a round may contain multiple calls. Track model turns, tool calls, retries, and elapsed time as distinct counters. Enforce a hard tool-call ceiling in addition to existing time and round ceilings.
4. **Plan evidence handoff is lossy.** Step results are copied into the shared transcript as assistant prose. Preserve structured outcomes and bounded tool observations as first-class execution state so dependent steps and final synthesis can use reliable evidence.
5. **Planner output is not a permission grant.** Keep the executor authoritative: a step marked parallel-safe may execute only read-only calls; mutations remain serialized and must pass the existing authorization/confirmation controls.

### P1 — reliability and maintainability

6. Separate orchestration state transitions from model prompting and tool adapters.
7. Make cancellation/deadline handling explicit and propagate it to model and tool calls where supported.
8. Make execution events structured, ordered, and correlated to a request, plan step, and tool call.
9. Add deterministic unit tests for DAG readiness, budget accounting, evidence isolation, recovery, and result ordering.
10. Preserve a direct-execution fallback when planning is unavailable or invalid.

## Target execution model

A request is represented by an execution context containing:
- a request ID and scoped principal;
- immutable request input and conversation context;
- an optional validated plan;
- step records with status, dependencies, attempts, timestamps, and bounded evidence;
- explicit budgets for elapsed time, model turns, tool calls, and retries;
- a cancellation signal;
- an append-only event stream for progress and diagnostics.

The orchestration kernel owns state transitions. The planner proposes a plan; deterministic validation checks its shape and dependency graph. The scheduler selects ready steps. The executor enforces tool schemas, permissions, concurrency and retry policy. The evaluator decides whether a model turn is complete or requests tools. The synthesizer receives the original request and verified execution record.

No model-generated field can expand permissions, budgets, concurrency, or retry limits.

## Delivery sequence

### Slice 1 — deterministic execution primitives
- Define typed execution budgets, counters, step states, and execution events.
- Add pure helpers for DAG readiness, terminal-state calculation, and budget reservation.
- Add tests for cycles, missing dependencies, failed prerequisites, and counter boundaries.
- No change to runtime behavior until these primitives are covered.

### Slice 2 — step-local evidence and structured outcomes
- Track observations produced by each step separately from inherited conversation context.
- Preserve bounded tool observations and model conclusions in the step outcome.
- Make final synthesis consume structured outcomes, not reconstructed prose alone.
- Ensure old conversation tool messages cannot affect a new step's status.

### Slice 3 — dependency-aware recovery
- Re-run readiness calculation after every state transition and recovery attempt.
- Permit dependents to proceed only when all prerequisites are completed.
- Keep recovery bounded and read-only by default; never automatically replay mutations.
- Ensure a recovered prerequisite can unblock its dependents.

### Slice 4 — hard budget enforcement
- Count each tool call, including retries, independently of model rounds.
- Reserve budget before execution; never start work that exceeds the remaining budget.
- Keep per-request elapsed-time and model-turn limits.
- Report which budget ended execution.

### Slice 5 — event and controller boundary
- Add request/step/tool correlation to internal events.
- Keep Telegram presentation as an adapter; do not leak Telegram concepts into the orchestration core.
- Extract orchestration kernel from the large controller incrementally.
- Preserve the existing five model-visible tools and current provider interfaces.

## Compatibility constraints

- Keep the custom Orchestra; do not introduce LangChain, LangGraph, or another agent framework.
- Keep the five current model-visible tools: `web_search`, `fetch`, `file_io`, `memory`, and `schedule`.
- Keep NVIDIA NIM, Neon PostgreSQL, and LightRAG integrations unchanged in this phase.
- Keep Telegram as the first interface, but keep core orchestration channel-neutral.
- Do not change v1 or production behavior through the v2 branch.
- Do not automatically retry mutations or weaken existing confirmation requirements.

## Definition of done

Orchestra 2.0 is ready when deterministic tests prove the execution-state invariants, the hard budgets cannot be exceeded, recovered dependencies are scheduled correctly, evidence remains attributable to its step, progress events are correlated and ordered, direct fallback remains functional, and the existing tool and Telegram behavior remains compatible. CI and deployed runtime verification are separate gates and must be reported separately.
