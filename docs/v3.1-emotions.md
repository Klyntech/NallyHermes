# v3.1 Affect Layer

This document describes the affect implementation introduced on the `v3.1-Emotions` branch. The layer is a lightweight conversational policy mechanism, not a psychological assessment or a durable user profile.

## Why two tracks exist

The implementation deliberately separates the current user's apparent conversational state from Nally's internal task state.

### User affect

`UserAffect` is inferred from the current message and contains:

- `valence`: negative to positive tone estimate.
- `arousal`: calm to activated estimate.
- `frustration`: frustration estimate.
- `warmth`: warmth estimate.
- `confusion`: uncertainty or blocked-understanding estimate.

The inference is heuristic and message-local. It does not establish how a person actually feels, and should never be presented as a clinical or diagnostic result.

### Agent affect

`AgentAffect` tracks internal conversational/task signals:

- `valence`
- `arousal`
- `confidence`
- `frustration`
- `curiosity`
- `updatedAt`
- `lastTopicKey`

The state is stored in memory per Telegram user ID. It is not persisted in Neon and resets when the process restarts.

## State transitions

Agent state is updated by events from the orchestration lifecycle:

| Event | Intended effect |
| --- | --- |
| `topic_change` | Reduce carried-over frustration and arousal; increase curiosity slightly |
| `tool_success` | Increase confidence, reduce frustration and improve valence |
| `tool_failure` | Increase frustration/arousal and reduce confidence/valence |
| `task_complete` | Increase confidence/valence and reduce frustration/arousal |
| `task_partial` | Slightly increase frustration and reduce confidence |
| `user_warm` | Add a small positive/curiosity adjustment |
| `user_frustrated` | Keep the agent response regulated; do not mirror the user's intensity |

Time decay moves the agent state toward a calm baseline. Topic changes use a lightweight topic key to prevent frustration from one task from bleeding into an unrelated task.

## Reply policies

The selector supports five outcomes:

- `urgent`
- `stress`
- `confuse`
- `warm`
- `baseline`

Priority is **urgent > stress > confuse > warm > baseline**.

| Policy | Communication behavior |
| --- | --- |
| `urgent` | Prioritize the immediate request and give the clearest next action |
| `stress` | Acknowledge the difficulty briefly, remain regulated, then act |
| `confuse` | Explain in plain language, reduce complexity and check whether the explanation resolves the confusion |
| `warm` | Use a proportionate amount of warmth without turning a greeting into an empathy monologue |
| `baseline` | Use normal concise conversational behavior |

The shared pattern is acknowledge → align → act. User frustration must not be mirrored as agent anger. Avoid theatrical empathy and avoid claiming that Nally literally feels human emotions.

## Prompt injection and decision influence

Affect can contribute a short prompt hint when the shift is meaningful and the channel is conversational. Near-baseline state should not add a hint. The layer also exposes bounded decision parameters such as risk tolerance, exploration preference, extra retry allowance and clarification preference.

These parameters are hints only. They do not override:

- System/developer safety policy.
- Tool permissions or connector allowlists.
- Universal write approvals.
- Provider-level write flags.
- Execution budgets, validation or failure handling.

## Configuration

`AFFECT_ENABLED` is a boolean environment setting and defaults to `true`. Set it to `false` to disable affect prompt/decision influence.

## Tests

`tests/affect.test.ts` covers:

- User frustration does not force agent rage.
- Confusion selects the explain-then-check policy.
- A short warm greeting does not create a monologue.
- Topic change reduces sticky frustration.
- Near-baseline affect produces no prompt injection.
- Topic keys are generated for ordinary phrases.

These are unit-level behavior checks. They do not prove emotion inference accuracy in real-world conversations.
